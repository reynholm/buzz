# Надёжная доставка результатов фоновой работы ACP

Постановка задачи для агента, которому передаётся реализация.

## Цель и порядок работы

Закрыть два ограничения механизма фоновых продолжений, добавленного в PR #17:

1. **Этап A, первый приоритет:** обычное новое сообщение не должно уничтожать ожидающий сбор результата фоновой работы или менять исходный адрес его доставки.
2. **Этап B, отдельное изменение:** повтор продолжения после частично успешного хода не должен создавать вторую публикацию одного итогового отчёта в управляемом механизме доставки.

Этапы должны иметь самостоятельные проверки и быть пригодны для отдельного ревью. Не задерживать исправление этапа A ради создания общего механизма этапа B. Не считать оба ограничения закрытыми после реализации только этапа A.

Это постановка требований, а не готовый план изменений API. Агент выбирает минимальный совместимый дизайн по текущему коду. До реализации этапа B явно описать идентификатор единицы доставки, место хранения состояния, путь публикации и границу гарантии.

## Этап A: сохранять ожидающий сбор результата

### Сценарий ошибки

1. Ход запускает фонового ребёнка и завершается.
2. Ребёнок завершается; harness ставит continuation в очередь. Возможен также уже начатый сбор, который завершился ошибкой и ждёт повтора.
3. Принимается новое сообщение в том же scope.
4. Continuation удаляется. Новый ход получает только обычный запрос.
5. Завершение ребёнка уже обработано, поэтому оно не создаёт нового уведомления о необходимости собрать результат.

Теряется запланированный сбор, а не обязательно байты результата: провайдер может сохранить результат в своей сессии. Полагаться на то, что следующий обычный ход сам его обнаружит, нельзя.

### Требования

- Хранить ожидающий сбор отдельно от обычных сообщений и сохранять его при их приёме. Удалить семантику молчаливого вытеснения во всех перечисленных путях, а не только в `push`.
- Сохранять исходные scope, worker/session ownership и root/parent треда. Новый запрос не должен переписывать происхождение уже существующего результата.
- Сохранить сериализацию: два `session/prompt` в одном scope не выполняются одновременно. Сообщение может отложить сбор или дополнить работу через steering; оно не означает отмену фонового результата.
- Выбрать и документировать порядок обработки нового сообщения и готового продолжения. При постоянном потоке сообщений сбор не должен бесконечно откладываться; при ошибках сбора обычные сообщения не должны попадать в бесконечную блокировку.
- Steering и отмена текущего foreground-хода, вызванная обычным новым сообщением, должны сохранять ожидающий сбор. Учесть режим `MultipleEventHandling::Interrupt`: прерывание хода не равно явной отмене фонового результата.
- Автоматическая ротация не должна уничтожать исходную сессию, пока её ожидающий сбор ещё нужен, включая период после выхода ребёнка и ожидание повторной попытки.
- Сохранить проверки поколений и владельцев. Никогда не собирать старый результат в заменённой сессии, выдавая её за исходную.
- Сохранить намеренную отмену по явным управляющим действиям `!cancel`/`!rotate` и очистку при потере членства в канале. Не возобновлять работу в канале после отзыва доступа.
- Сохранить backoff и конечный бюджет повторов. Терминальный сбой должен быть видимым там, где доступ ещё разрешает уведомление; переполнение или истечение срока ожидания не должны молча уничтожать обязательство доставки.
- Ограничить объём удерживаемого состояния и исключить busy loop. Ожидающее продолжение не должно потеряться при idle-pool sleep или обходе heartbeat.

Граница этапа A: гарантируется сохранение и обработка ожидающего сбора в пределах работающего harness. Успешный `session/prompt` сам по себе не является подтверждением публикации. Восстановление после смерти самого harness и идемпотентность публикации относятся к этапу B.

### Критерии приёмки и регрессии

- [ ] Готовый continuation переживает новое принятое сообщение; в итоге отправляется запрос сбора в исходную ACP-сессию и с исходным тредом.
- [ ] Если обычное сообщение уже стоит в очереди до обнаружения выхода ребёнка, обязательство собрать результат всё равно сохраняется.
- [ ] Новое сообщение во время backoff не удаляет continuation; выбранная политика повторов сохраняет конечный бюджет.
- [ ] Сообщение во время выполняющегося сбора не создаёт параллельный ход. Проверены queue, steer и interrupt paths, в том числе отмена для повторного prompt.
- [ ] При `session-policy=channel` запрос из другого треда того же канала не перенаправляет прежний результат. При `Thread` и для DM сохраняются их границы.
- [ ] Новое сообщение во время живого ребёнка не перезаписывает исходный маршрут его результата.
- [ ] Автоматическая ротация, в том числе `--max-turns-per-session 1`, ждёт обработки сохранённого продолжения. Явная ротация и отзыв доступа не возобновляют старую сессию.
- [ ] Сбор работает с выключенным idle sleep и без lazy pool; исчерпание повторов имеет конечный исход.

Нынешний `real_message_supersedes_a_retrying_continuation_without_backoff` закрепляет ошибочную семантику. Изменить его вместе с production-путём. Одного queue unit test недостаточно: добавить проверку через `dispatch_pending` и локальный ACP-адаптер с реальными дочерними процессами, управляемыми маркерами вместо произвольных задержек.

## Этап B: идемпотентная доставка итогового отчёта

### Сценарий ошибки

1. Follow-up выполняется в исходной сессии и успешно публикует отчёт.
2. Следующий запрос модели в том же ходе возвращает application error.
3. Harness сохраняет сессию для `AgentError` и повторяет continuation.
4. Агент снова вызывает отправку, например с изменённой сводкой или позже по времени. Получается другой event ID, и relay сохраняет второе сообщение.

Этот путь существует в bundled `buzz-agent`: исполнение tools — `agent.rs:793`, следующий запрос LLM — `agent.rs:409`, возврат ошибки — `agent.rs:503`, сохранение истории — `lib.rs:837`. `buzz-acp` сохраняет сессию для `AgentError` в `pool.rs:3655`. Не утверждать, что все ошибки возвращаются в ту же сессию: transport/fatal failures могут инвалидировать её.

### Требования и граница гарантии

- Ввести стабильную идентичность конкретной доставки итогового отчёта. Она сохраняется между попытками; новые `turn_id`, generation, PID или текст отчёта не должны служить её единственным ключом.
- Единица доставки может соответствовать наблюдаемой группе фоновых процессов, как в текущем harness. Не обещать идентичность отдельных внутренних задач провайдера, если ACP не передаёт такой идентификатор.
- Не применять один ключ ко всем сообщениям задачи: промежуточная публикация не должна блокировать финальный отчёт, а два разных завершения не должны взаимно подавляться.
- Обеспечить гарантию в коде управляемого пути публикации. Изменение промпта или надежда на сохранённую историю не считается выполнением требования.
- Предпочтительный вариант: журнал исходящих доставок с ключом доставки, исходным маршрутом, подготовленным подписанным Nostr-событием и подтверждением принятия relay. Повтор использует те же подписанные байты; при ambiguous outcome запись сохраняется для повтора именно этого события.
- Сохранить запись до отправки, чтобы сбой между записью события на relay и локальным подтверждением не заставлял повторно строить другой event ID. Обеспечить атомарное создание записи и последовательную обработку конкурентных попыток одного ключа.
- При повторе того же ключа с изменённым содержимым не создавать второй пост. Выбрать явный контракт: возврат уже существующей доставки либо конфликт содержимого. Обновление опубликованного отчёта должно быть отдельной явно заданной операцией.
- Для выбранного журнала проверить восстановление после перезапуска владельца состояния. Не удалять неподтверждённую запись до успешного повтора или явно зафиксированного терминального исхода.
- Ограничить журнал, время/число повторов и срок хранения подтверждений. Указать срок действия идемпотентности после очистки записей; не обещать бессрочную гарантию при конечном журнале.
- Проверять исходный канал и актуальный доступ при доставке. Отзыв доступа не должен приводить к публикации через другой канал или личную переписку.
- Агент-facing интерфейс размещать в `buzz-cli` и использовать существующую Nostr-публикацию. Не добавлять отдельный relay HTTP endpoint без необходимости; текущая дедупликация event ID должна использоваться повторно.
- Определить, какие CLI/MCP-пути реально проходят через механизм. Нельзя заявлять общую exactly-once гарантию, если провайдер может опубликовать отчёт через обходящий его инструмент. Достаточна явно ограниченная гарантия для управляемого пути доставки фоновых отчётов.

Не требуется универсальная однократность всех произвольных shell/MCP-действий агента. Дедупликация terminal frames по `tool_call_id` сама по себе также не подтверждает однократность публикации.

### Критерии приёмки и регрессии

- [ ] Реальный production-путь публикации записывает отчёт, затем ACP-ход получает application error; повтор доставки сохраняет ровно одно видимое событие.
- [ ] Повтор того же delivery key с изменённой сводкой не создаёт второй пост; проверен выбранный контракт конфликта/повторного ответа.
- [ ] Два различных completion/delivery key дают два отчёта, даже при одинаковом тексте.
- [ ] Две конкурентные попытки одного ключа не создают два разных signed event ID.
- [ ] Потеря ответа после сохранения события на relay приводит к повтору тех же байтов, а не к повторному построению события.
- [ ] Сбой после принятия relay, но до локальной отметки, и перезапуск владельца журнала не создают повторную публикацию.
- [ ] Промежуточные сообщения, другой completion и явное редактирование отчёта не подавляются ошибочно.
- [ ] Отзыв доступа, terminal retry limit, очистка журнала и ресурсные ограничения имеют проверенное поведение.

Считать уникальные подписанные события/видимые посты, а не HTTP-запросы: транспортные повторы допустимы. Тесты должны вызывать production publisher, не только test-only helper. При удалении стабильного ключа или повторном построении события регрессия должна воспроизводиться.

## Проверка и результат работы

На исходной версии выполнены следующие проверки; результаты не относятся к будущей реализации:

```sh
  -u BUZZ_ACP_LAZY_POOL \
  -u BUZZ_ACP_IDLE_POOL_SLEEP \
  cargo test -p buzz-acp background -- --test-threads=1

cargo test -p buzz-cli stored_event_body_loss_is_retried_with_same_event_bytes -- --test-threads=1
# 1 passed, 0 failed
```

После каждого этапа запускать соответствующие регрессии, полный пакет затронутой поверхности, форматирование и clippy. Для ACP очищать перечисленные переменные и выполнять пакет последовательно, как указано в package TESTING.md. Перед PR выполнить `just ci`; если затронуты relay/db/auth — также `just test` с необходимой инфраструктурой.

Для этапа A упражнять реальный локальный ACP/process workflow; для этапа B — publication/readback и неоднозначный исход. Детерминированные локальные адаптеры и модель допустимы, но в отчёте отличать mock relay от настоящего relay и agent testing от human testing. Не объявлять реальную публикацию проверенной только по количеству отправленных prompt.

Итоговый отчёт должен содержать:

- Какие критерии выполнены для A и B и где проходит граница гарантии.
- Изменённые исходники и краткое объяснение выбранной модели состояния/доставки.
- Команды и фактические результаты проверок, воспроизводимые сценарии и ограничения.
- Точные шаги ручной проверки и признаки работающего поведения.
- Оставшиеся ограничения провайдеров, топологии процессов и восстановления после сбоев.

Не менять процесс отслеживания detached/reparented children и не включать посторонний рефакторинг. Не добавлять `unsafe`, production `unwrap`/`expect`; новые public API документировать. Перед Git и hooks активировать Hermit; коммиты, если создаются, выполнять с `git commit -s`.
