# Buzz fork: агенты на своих устройствах

Дата: 2026-10-03. Статус: дизайн на рассмотрении владельца, код не реализован.
Ветка: `fork/device-bound-agents`. База: `desktop-v0.5.26`,
`2b4b138dc5cf2d9cc1a0ceb21d9063ff56fe8bf4`.

## 1. Основание и результат

Исходная постановка владельца: `/Users/reynholm/www/buzz-fork.md`.
Поручение в Buzz: `162dd0a6bd0c174b6930cc63144655a0fe67c972158139116eb881c61c630f30`.
Дополнение из этого поручения приоритетнее исходной постановки:
при создании агента владелец выбирает, разрешён ли запуск на других
его устройствах. По умолчанию разрешение выключено. Включённое разрешение
сохраняет существующее поведение Buzz.

Цель: агент с выключенным разрешением остаётся виден на втором ноутбуке,
но никакой UI, команда или автоматика не создаёт и не запускает там его
экземпляр. Карточка объясняет, где агент размещён, и показывает наличие
связи с relay. Агент с включённым разрешением запускается как сейчас.

В скоупе также: редактируемое имя устройства, миграция существующих агентов,
сопровождение desktop-форка из релизных тегов upstream, проверенный
Apple Silicon артефакт. Установку на рабочие ноутбуки выполняет владелец.
Перенос между машинами, автоматическое исправление существующих дублей,
изменения relay/mobile, Developer ID и нотаризация не входят.

Этот документ конкретизирует исходную постановку; существенные уточнения
отдельно перечислены в §3. Они предложены для проверки владельцем.

## 2. Подход и ограничения продукта

Выбран backend-барьер с проекцией решения в UI. Скрытие Start само по себе
не закрывает onboarding, создание команды, восстановление и прямой IPC.
Только запрет импорта карточки тоже не подходит: карточка должна оставаться
видимой. Relay-координация запуска потребовала бы изменения серверной модели
и выходит за согласованный desktop-скоуп.

Одна Rust-политика отвечает за создание, запуск, рестарт и удаление
определения; фронтенд показывает её результат. Новые модули изолируют
политику и сведения устройства. В существующий код добавляются точки
вызова, покрытые проверками, без смены модели runtime/provider.

Связь с продуктовой моделью: [VISION.md](../../../VISION.md) и
[VISION_REMOTE_AGENTS.md](../../../VISION_REMOTE_AGENTS.md) допускают
сменяемый исполнитель при сохранении identity. Наше ограничение — выбор
владельца о запуске определения на своих Desktop, а не новый substrate
control plane. Для разрешённого шаринга remote-provider поведение сохраняется.
Для запрещённого шаринга только домашний Desktop вправе инициировать
create/start/redeploy; выполнение у выбранного им provider остаётся
существующим односторонним deploy. Наличие связи не доказывает здоровье
процесса, поэтому UI не обещает больше relay-presence.

## 3. Уточнения исходной постановки

1. **Копия локальной записи не делает машину домашней.** В исходном §4.3
   любой экземпляр побеждает чужой origin, но §4.4 требует блокировки копии
   `managed-agents.json`. Здесь локальным считается экземпляр с проверенной
   привязкой к текущему устройству; простой файл с pubkey/auth_tag этого
   не доказывает. Отдельный локальный маркер в системном keychain позволяет
   отличить копирование JSON от удаления `device.json` на той же машине.
2. **Удаление последнего экземпляра освобождает определение явно.**
   Остаточный чужой origin иначе навсегда блокирует критерий 14. Домашняя
   машина публикует освобождение вместе с tombstone экземпляра. На второй
   машине Start появляется после получения обоих изменений; остановка
   процесса или offline сами по себе ничего не освобождают.
3. **Legacy без нового разрешения трактуется как запрет шаринга.** Это
   предложение для миграции существующих агентов по исходным критериям 15–16;
   явное разрешение `true` включает старое поведение. Отсутствие поля
   сохраняет старые байты сериализации, а не означает автоматическое согласие.
4. **Переключатель выбирается при создании.** В v1 у существующей карточки
   показывается сохранённая политика без операции переноса или смены дома.
   Редактирование имени/prompt/runtime остаётся доступным. Добавлять смену
   разрешения после создания и разбирать уже запущенные на двух машинах
   экземпляры этот дизайн не предлагает.

## 4. Модель

### 4.1. Публичная политика определения

`AgentDefinition` и его keyless-представление в unified store получают:

| Поле Rust/wire | Семантика |
|---|---|
| `share_across_devices: Option<bool>` | `true` — нынешнее поведение; `false` и отсутствие — привязка к дому |
| `origin_device_id: Option<String>` | UUID текущего домашнего Desktop |
| `origin_device_label: Option<String>` | Отображаемое имя дома |
| `origin_released: Option<bool>` | Явное освобождение дома после удаления последнего экземпляра |

В TS соответствуют camelCase-поля. Это не существующий `shared`:
`shared` описывает публикацию в каталоге сообщества, scoped по relay+owner
([локальные правила](../../../desktop/src/features/agents/AGENTS.md), правило 10).

Поля добавляются в конец `PersonaEventContent` kind:30175, с
`serde(default, skip_serializing_if = "Option::is_none")`.
Все четыре исключаются из `persona_content_hash`: политика запуска и
происхождение не изменяют конфигурацию уже выполняющегося процесса.
Reference vectors без полей остаются байт-в-байт прежними.
Описание optional fields в NIP-AP обновляется, серверных правил не требуется.

Новые определения всех путей получают текущие origin и
`origin_released = false`, а разрешение — явно выбранное значение или `false`.
Источники: диалог, owner-reviewed draft, обычный импорт, snapshot, каталог,
team pack и материализация builtin. Foreign-каталог и переносимый snapshot
не задают привязку или разрешение владельца: это новая локальная копия,
по умолчанию без шаринга. Снапшоты не экспортируют эти четыре поля.

### 4.2. Сведения и локальное доказательство устройства

`device_identity.rs` хранит `<app_data_dir>/device.json`:
`{device_id, label, created_at}`. `device_id` — UUID v4, `label` по умолчанию
hostname. Запись атомарная; конкурентные инициализации сериализованы.
Команды: `get_device_identity` и `set_device_label`.

Отдельный случайный UUID-маркер хранится только в несинхронизируемом локальном
keychain под отдельным service `buzz-desktop-device-host`. Он не относится
к identity владельца и не очищается при обычной смене сообщества/владельца.
Не используется процесс-global `SecretStore::shared`, привязанный к одному
service; отдельный store создаётся через существующий `SecretStore::keyring`.
Генерация и запись маркера имеют блокировку и проверку фактического сохранения.
Fallback маркера в `managed-agents.json` или `device.json` запрещён.

Связанные экземпляры получают локальное поле
`device_host_binding: Option<String>` с этим маркером. Оно не уходит в
30177, каталог или snapshot. Для запрещённого шаринга mismatch запрещает
spawn независимо от имеющихся pubkey, auth_tag и inline key.

Удаление только `device.json` на A создаёт новый публичный `device_id`,
но сохраняет keychain-маркер: экземпляры A остаются доказанно локальными,
origin переклеймляется на новый id, и 30175 ставится в durable очередь.
Копия JSON с A на B не содержит маркера в keychain B и не запускается там.
Если связанная запись уже имеет binding, а keychain недоступен или потерян,
она не переклеймляется автоматически; возвращается ошибка с возможностью
повторить после восстановления доступа. Полный перенос keychain/клонирование
ОС не является сценарием копирования JSON и не считается доказанной защитой.

### 4.3. Legacy-клейм

Boot выполняет миграцию после fold/detach и до sync/restore.
Legacy-экземпляр без binding с реально доступным локальным ключом
может быть привязан к текущему маркеру. Пустой pubkey/auth_tag без ключа
не создаёт доказательство. Legacy inline-key записи до первой миграции
невозможно отличить от их побайтовой копии: это фиксируется в отчёте,
а не выдаётся за защиту от исторического копирования.

При конфликте такого legacy-экземпляра с уже явно чужим origin он не
получает автоматический клейм. Без конфликтующего origin первый клейм
выполняется на машине с ключом, ставит binding и origin, затем публикует
30175. Legacy-определения без экземпляра не присваиваются машине на boot:
30177 определяет remote-дом; при отсутствии доказательств это `unclaimed`.
Миграция идемпотентна; ошибку чтения/сохранения нельзя превращать в успех.

## 5. Классификация и действия

`definition_home.rs` принимает определение, локальный набор экземпляров,
текущее устройство и проверенные owner-события активного relay.
Запросы retention scoped по relay+owner; нельзя искать по одному имени
или использовать события чужого автора.

| Состояние при выключенном разрешении | Классификация и результат |
|---|---|
| Есть экземпляр с совпавшим binding | `local`, create/start разрешены на доме |
| Есть экземпляр с чужим binding | `remote`, spawn этой записи запрещён |
| Нет локального экземпляра, есть активный 30177 другого устройства | `remote`, Start и Delete определения запрещены |
| Нет экземпляра, origin чужой и не освобождён | `remote`, Start и Delete определения запрещены |
| Origin свой, экземпляра нет | `local`, Start разрешён |
| Origin пуст либо явно освобождён, активных 30177 нет | `unclaimed`, Start разрешён; успешное создание фиксирует новый дом |

Разрешение `true` отключает новые ограничения, сохраняя существующие
предварительные проверки runtime, ownership и provider. Представление дома
может оставаться информационным. `origin_released` не перебивает активный
30177: порядок доставки release и tombstone не открывает ранний Start.

Ответ `list_personas` содержит computed `home` с kind/label/pubkeys и
вычисленные возможности действий. Это проекция, не сохранённый второй
источник политики. Ошибка чтения home не заменяется `unclaimed`.
`remoteInstancePubkeys` содержит только активные retained 30177;
для информации о связи UI обращается к существующему relay-agent query.

Backend использует тот же модуль под `managed_agents_store_lock` перед
mint ключей и повторно перед фиксацией записи, если операция отпускает
lock на `.await`. Информация scope фиксируется до await; смена сообщества
не перенаправляет операцию. Нельзя держать std-mutex через await.
При запрете возвращается `definition_hosted_elsewhere` и label дома.

Барьеры охватывают create, ручной start/restart, restore, reconcile,
access-policy restart из inbound и нижнюю общую точку spawn/preflight.
Это закрывает прямые команды и будущие UI-пути. Новые записи не могут
подделать binding через входной IPC: он присваивается backend.
Legacy definition-less экземпляры остаются вне классификации по исходной
постановке; проверка нового диалога должна подтвердить, что он создаёт
определение и не обходит выбранное разрешение.

Удаление remote-определения проверяется также backend до cascade, keyring
cleanup и подписания kind:5. Не следует блокировать получение валидного
owner-tombstone домашней машины — оно должно удалять синхронизированное
представление. Нельзя публиковать локальные изменения от копии чужой записи.

## 6. Обновления и освобождение дома

Inbound 30175 сначала проходит существующее newest-wins разрешение retention.
Отсутствующие поля старого клиента не очищают известную явную политику и
дом. Явные origin/release-поля принятого нового head обновляют карточку без
локального proven-экземпляра. Для proven-экземпляра сохраняется его местный
дом; он не переезжает от эха или чужого origin. Разрешение в v1 не меняется
через общий диалог редактирования, но owner-sync переносит явное значение.

Удаление последнего доказанно домашнего экземпляра при выключенном
разрешении в одной сохраняемой версии unified store удаляет экземпляр и
ставит `origin_released = true` на оставшемся определении. Сохраняются
origin id/label как lineage; политику они больше не блокируют без активных
экземпляров. Подписанные 30175 release и kind:5 для 30177 сохраняются в
durable retention до сообщения об успехе. Существующий assignment-cleanup
journal не покрывает release и публикацию; новый `device_home_operations.rs`
добавляет узкий журнал домашних операций. До удаления JSON-записи атомарно
сохраняется намерение: operation id, target pubkey/persona, исходный
relay+owner scope и подписанные public-события. Секреты и keypair в журнал
не попадают. После единого save unified store одной SQLite-транзакцией
enqueue-ятся release, tombstone и существующая NIP-IA archive-операция;
журнал очищается только после durable enqueue.

Recovery до restore завершает начатое удаление под тем же store-lock и
проверяет актуальные записи перед освобождением дома: появление нового
локального экземпляра не должно быть стёрто старым release. Scope журнала
не заменяется текущим сообществом. Повтор применяет те же подписанные
события идемпотентно, не создаёт новые ключи и не теряет исходное намерение
при ошибке. После enqueue публикации выполняет существующий event-sync.

Остановка процесса не освобождает дом. Удаление одного из нескольких
экземпляров на доме не освобождает его. При разрешённом шаринге специальный
release не меняет нынешний lifecycle. На B `unclaimed` достигается только
после доставки release и удаления соответствующего retained 30177.

`get_retained_events_by_kind` уже существует;
`commit_inbound_tombstone_with_store` уже атомарно сохраняет tombstone и
чистит covered head. Используем их, включая timestamp-проверки, вместо
нового параллельного tombstone-алгоритма. После новых head/tombstone
обновляется локальная persona-проекция, без ложной инвалидизации каталога.

Смена label перепубликовывает домашние определения, которым соответствует
текущий публичный origin; исключение полей из hash исключает restart badge.
Операция сначала сохраняет label и durable retry-worklist в этом же журнале
для перепубликации (тип операции label, scope и затронутые определения);
при недоступности relay состояние остаётся queued. Неудачный enqueue не
считается успешным завершением изменения на других устройствах.

## 7. Интерфейс

В Create: переключатель «Разрешить запуск на других моих устройствах»
с выключенным значением и пояснением «При включении на другой машине
можно создать отдельный экземпляр этого агента». Он не называется
«Поделиться», чтобы не смешиваться с каталогом и доступом других людей.
Сохранение выбранного значения проходит через единый create request;
неявное создание и draft без поля используют `false`.

Карточка remote-агента с запретом сохраняет аватар, имя и описание.
Start и Delete отсутствуют; вместо runtime control — компонент с
`data-testid="persona-runtime-remote-<id>"`. Бейдж:
«На устройстве <label> · в сети/не в сети»; неизвестный label —
«На другом устройстве». Статус определяется по pubkeys, а не по имени.
Edit сохраняется, с «Работает на: <label>» и информацией о политике.

Пять путей через `buildInstanceInputForDefinition` и отдельный
`channelAgents`/team reuse проверяют computed возможности до вызова
mutation. Для onboarding/team — пропуск с объясняющим уведомлением,
в интерактивном intent `definition_start` — недоступность действия с
причиной. Profile, меню, массовое удаление команды и диалог выбора
места запуска также применяют возможности. Остальные операции команды
не должны молча удалять её remote-членов через другой backend cascade.
Новый прямой вызов builder вне перечисленного списка делает тест красным.

Settings → Agents: «Имя этого устройства», валидация непустой trimmed
строки, сохранение и состояние ошибки/queued. Управление доступно
клавиатурой, статус текстовый, не только цветовой. Следуем существующей
системе компонентов и rem-токенам.

## 8. Форк и обновления

Используем уже существующий `reynholm/buzz`, не создаём дубль репозитория.
`upstream` — FF-зеркало main; `fork/main` — релизный тег с нашими коммитами;
`fork/sync-vX.Y.Z` — временная ветка merge нового тега без rebase;
`fork-vX.Y.Z-N` — проверенное состояние сборки. Версия приложения и bundle
identifier сохраняют upstream-значения. About добавляет номер форка и SHA
через новый build_identity-модуль.

`FORK_PATCHES.md` фиксирует базовый тег и SHA, каждый изменённый upstream
файл, точку вызова, назначение и falsifiable-проверку. Вне реестра выбирается
upstream; потерянный seam, удаление/переименование нашего модуля либо
неразрешимый конфликт останавливают обновление с draft PR и отчётом.
Снятие патча в пользу аналогичной upstream-фичи требует решения владельца.

Ежедневный и ручной запуск ищет последний новый `desktop-v*`, перечисляет
пропущенные теги, создаёт merge-ветку и запускает обязательные проверки.
Нет новых тегов — нет сообщений. Runner/agent переносит перечисленные
patch seams; неразрешённые конфликты публикуются для рассмотрения без
автоматического слияния. Идемпотентность по версии и serialization запуска
не допускают повторных sync-веток/PR на один тег.

Сборка только `aarch64-apple-darwin`: сначала cargo release для реальных
`buzz-acp`, `buzz-agent`, `buzz-backend-kubernetes`, `buzz-dev-mcp`,
`git-credential-nostr`, `buzz-cli`, затем `scripts/bundle-sidecars.sh`
и `just desktop-release-build`. Проверяется архитектура, ненулевой размер
и executable-mode каждого sidecar; заглушки не являются готовым артефактом.
Upstream updater endpoints остаются пустыми и не заполняются release env.
Проверка охватывает реальный bundled config/ресурсы, а не только source JSON.

Артефакт и SHA256SUMS привязаны к точному candidate SHA. До владельческого
merge/tag — draft release/candidate artifact, а не финальный fork-tag.
PR содержит диапазон тегов, changelog, agent/persona/sync изменения upstream,
конфликты, результаты с SHA и ссылку на артефакт. Merge выполняет владелец.
После merge подтверждается совпадение дерева кандидата с итогом, затем
ставится fork-tag, обновляется release и удаляется sync-ветка.
Финальный тег не создаётся заранее из ещё не принятого merge-кандидата.

Первый чистый upstream build обязателен для сравнения. На красном чистом
теге pipeline фиксирует upstream-блокер; не чинит его незаметно нашим патчем.
Первый настоящий upgrade-тест требует следующего тега после 0.5.26.
На 2026-10-03 `git ls-remote` подтвердил 0.5.26 и не вернул 0.5.27;
критерий реального следующего обновления не может считаться уже выполненным.
