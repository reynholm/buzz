# Buzz fork: видимые и управляемые сессии агентов

Дата: 2026-10-10. Статус: дизайн принят по разделам, спека на ревью владельца, код не реализован.
Ветка: `fork/session-continuity`. База: `fork/main`, `bb99d224a81aa25808101c48442f9e7b2b8563c5`.
Связанные задачи форка: reynholm/buzz#6 (resume сессий), reynholm/buzz#7 (скрытый 15-минутный сон пула).
Отдельный дизайн для #7: `2026-10-10-idle-clock-turn-completion-design.md`.

## 1. Основание и результат

Агент в треде теряет сессию модели, и этого никто не видит. Сон ленивого пула
(`BUZZ_ACP_IDLE_POOL_SLEEP=900`, Desktop ставит его жёстко) сносит сессии всех
тредов агента разом: по логам harness с 29.09 это от 1 до 15 раз в день на агента.
Новая сессия получает корень треда и последние 12 сообщений, а агент о потере
догадывается только по `truncated="true"`. Человек не видит ни потери, ни
заполненности контекста, и не может ни продолжить, ни начать заново по своему выбору.

Проблема в трёх слоях: потеря, невидимость, отсутствие управления. #7 закрывает
часть первого слоя, #6 — первый слой целиком. Второй и третий не закрывает ни одна.

**Решения владельца, принятые в обсуждении (10.10.2026):**

1. Главное — прозрачность и контроль, плюс починка багов. Модель «как в терминале»:
   человек видит процент контекста и сам решает, когда сжать или начать заново.
2. Работаем своими силами в форке, upstream не ждём. Спеки и решения храним
   в репозитории, чтобы разрешать конфликты синхронизации.
3. Видят все участники треда. Управляет тот, кому агент разрешает давать задачи
   по настройке «Кто может давать инструкции» (`RespondTo`).
4. Обрыв инфраструктурой (сон пула, рестарт, падение воркера): агент продолжает
   сам через resume и показывает это. Начать заново решает человек.
5. Стартовое сообщение агента в треде не усложняем: новая сессия просто
   гарантированно его получает. Про tempo и другие скиллы Buzz ничего не знает.
6. Управление: «Сжать» и «Начать заново» с глубиной «с нуля / последние / весь тред».
   Число сообщений в UI не называется.
7. Транспорт — обычные сообщения чата (подход A): теги на ответе агента
   и команды текстом. Релей и протокол не меняются.

**Результат.** В любой момент по треду видно, в каком состоянии сессия каждого
агента, почему она новая и насколько заполнен контекст. Обрыв инфраструктурой
незаметен для работы. Человек одним действием сжимает контекст или начинает заново.

**Не входит:** автоматический повтор хода, оборванного падением воркера
(это upstream #8145); `session/load` с проигрыванием истории; новые kinds событий;
порог «продолжать, только если контекст ниже X%»; отдельная настройка прав на сессию.

## 2. Почему сброс сессии не задуман как фича

Сон пула ввели в block/buzz#5682 ради ресурсов («216 workers that never shrink»),
о свежести контекста там ни слова. Окно 12 и корень треда появились в #69 для
холодного старта, когда агента зовут в уже идущий тред. Живая сессия по замыслу
помнит: harness шлёт ей только новые события (`ChannelDeliveryState`, `pool.rs:114`).
Явный сброс уже есть и включается намеренно: `--max-turns-per-session`, ротация
при переполнении контекста, `!rotate`. Upstream считает потерю дефектом
(#5342 открыт), но resume-PR #6088/#6990 стоят с августа.

Окно 12 и корень треда остаются: ими пользуется каждая новая сессия (раздел 5).

## 3. Разбиение работы

| # | Кусок | Что даёт |
|---|---|---|
| 1 | #7: часы простоя обновляются при завершении хода | ход длиннее 15 минут не теряет сессию сразу после ответа |
| 2 | Resume и сохранение состояния доставки | после сна агент продолжает и получает только дельту |
| 3 | Видимость | строка «новая/продолжена · причина · контекст N%» у ответа каждого агента |
| 4 | Управление | «Сжать», «Начать заново» с глубиной, права по `RespondTo` |
| 5 | Холодный старт | новая сессия гарантированно получает стартовое сообщение агента |

Порядок: 1 → 2+5 → 3 → 4. Видимость раньше управления, чтобы сначала увидеть
реальную картину. Эта спека описывает куски 2–5, у куска 1 свой короткий дизайн.
Каждый кусок — свой план. Вся работа (спеки, планы, код всех кусков) идёт
одним PR в `main` форка, куски — последовательными коммитами в порядке выше.

## 4. Модель состояния и видимость

### 4.1. Состояние скоупа

Скоуп — это `SessionScope` (`scope.rs:71`): тред или вся беседа (канал при
политике Channel, DM). Состояние на скоуп:

- **state:** `new` | `resumed` | `compacted` | `restarted`;
- **reason:**
  - инфраструктура: `first_in_thread`, `idle_sleep`, `harness_restart`, `worker_crash`;
  - авторотация и сбои: `resume_failed:<код>`, `config_changed`, `context_overflow`, `max_turns`;
  - команды человека: `user_restart:<none|recent|all>`, `user_compact`, `auto_compact`; для команд хранится автор;
- **context:** `used/size` из `usage_update`, отсюда процент;
- **thread:** для новой сессии — «прочитано N из M».

### 4.2. Как состояние попадает в тред

Ответ в тред публикует сам агент через `buzz messages send`, а не harness.
Поэтому:

1. harness ведёт маленький файл статуса на скоуп и обновляет его при старте
   или продолжении сессии, на каждом `usage_update` и на `compaction_update`;
2. путь к каталогу harness передаёт агенту через переменную окружения
   (по образцу `BUZZ_AUTH_TAG`, который CLI уже читает из окружения, `client.rs:1098`);
3. `buzz messages send` определяет скоуп ответа (канал и корень треда CLI уже
   вычисляет по NIP-10 из `--reply-to`, `messages.rs:42`), читает файл и добавляет тег:
   `["buzz-session", "<state>", "<reason>", "<percent>"]`.

Kind 9, релей и протокол не меняются. Агент без нашего CLI строку не получит,
но ничего не ломается. Альтернатива «harness пишет системное сообщение при смене
состояния» отклонена: лишнее сообщение, и стоит оно не у ответа.

### 4.3. Что видит человек

Под ответом каждого агента — короткая приглушённая строка:

- после смены состояния, один раз: «Продолжена после сна · 64%»,
  «Новая · resume не удался: транскрипт не найден · прочитано 12 из 37»,
  «Сжато по команде <имя> · 18%»;
- на остальных ответах только процент; от 80% он подсвечивается.

Строку Desktop рисует только у сообщений агентов. Тег агент ставит о себе сам
и сообщает только о собственной сессии.

### 4.4. Что видит агент

В промпт новой или продолженной сессии добавляется маркер
`<session state="resumed" reason="idle_sleep">`; для новой сессии ещё
«прочитано N из M». Агенту не нужно угадывать потерю по `truncated`.

### 4.5. Ограничения

- Процент приблизительный. Claude присылает `usage_update` в конце хода,
  поэтому ответ посреди хода несёт значение на его начало. Codex шлёт данные
  в процессе. Знак «≈» не пишем, иначе строка шумит.
- Сейчас harness читает `usage_update` только у Claude: для остальных адаптеров
  `handle_standard_usage_update` сразу выходит (`acp.rs:1940`). Для процента
  у Codex (`codex-acp` шлёт `{used,size}`) это ограничение снимается.

## 5. Resume, дельта и холодный старт

Всё в этом разделе — сторона harness (`buzz-acp`).

### 5.1. Хранилище сессий

Новый модуль `session_store.rs`; в `pool.rs` и `lib.rs` только тонкие швы
(правило форка о минимальных правках upstream-файлов). Одна запись на скоуп:

- адаптер и `session_id`;
- `cwd`;
- отпечаток конфигурации: модель + хэш системного промпта;
- поколение скоупа;
- причина, по которой сессия ушла из памяти;
- состояние доставки: id уже переданных событий (с лимитом) и флаг «стоячий
  контекст отправлен».

Каталог хранилища задаёт Desktop через переменную окружения. Файлы статуса
для CLI (раздел 4.2) лежат там же, отдельно от записей: CLI читает только
маленький файл статуса и не разбирает запись целиком.

### 5.2. Жизнь записи

- **Остаётся** (сессию можно продолжить): сон пула, shutdown, respawn, падение
  воркера. Сейчас в этих местах сессия стирается совсем (`lib.rs:3612`, `:3728`,
  `:4088`, вызовы `invalidate_all` в `pool.rs`). Теперь стирается только память
  процесса, а в запись пишется причина ухода.
- **Удаляется** (новая сессия по решению): «Начать заново», `!rotate`,
  `max_turns`, переполнение контекста.

### 5.3. Продолжение

Следующий ход в скоупе без живой сессии:

1. **Fencing.** Скоуп может переехать на другой воркер (`try_claim`, `pool.rs:1061`;
   `ForkAfterHold`, `pool.rs:1040`). Если у скоупа есть живой владелец, запись
   не трогаем. Проверка по поколению — правило №2 из Review-Proven Rules.
2. **Конфигурация.** Claude при resume передаёт процессу текущий
   `_meta.systemPrompt`, поэтому продолженная сессия получает новый промпт
   и старую историю. Правило `config_changed` (новая сессия при смене модели
   или промпта) оставляем запасным; точный список случаев по каждому адаптеру —
   в плане, по Codex не проверено.
3. **Возможности адаптера.** Если адаптер объявил `sessionCapabilities.resume`
   в `initialize`, вызываем `session/resume`. Сейчас harness из ответа
   `initialize` читает только steering (`acp.rs:687`). Оба адаптера resume
   объявляют (`claude-agent-acp` 0.79.0, `codex-acp` 2.2.2). `session/load`
   в первую версию не берём: он проигрывает всю историю, а таймаут запроса
   60 с (`acp.rs:1165`).
4. **Ошибка.** Любая ошибка ведёт к новой сессии с причиной `resume_failed:<код>`;
   запись заменяется новой.
5. **Успех.** Восстанавливаем состояние доставки. Дальше работает существующий
   фильтр `conversation_context_delta` (`pool.rs:4034`): приходят только
   сообщения после паузы и триггер. Стоячий контекст повторно не шлём.

### 5.4. Холодный старт

Новая сессия собирает контекст по глубине:

- **последние** (по умолчанию и для инфраструктурных причин): корень + первое
  сообщение треда с упоминанием этого агента, если это не корень, + окно по
  `BUZZ_ACP_CONTEXT_MESSAGE_LIMIT`. Как дёшево найти первое упоминание без
  выкачки всего треда — в плане;
- **весь тред:** все сообщения с потолком по байтам; если тред не влезает,
  берём начало и хвост, строка честно пишет «прочитано N из M»;
- **с нуля:** только триггер и стартовое сообщение агента.

Маркер `<session state reason>` и «прочитано N из M» добавляются в промпт.

### 5.5. Не входит

Если ход оборвался посреди работы (упал воркер), resume вернёт историю, но
недоделанный ход заново не запустится. Человек видит «продолжена после падения»
и повторяет запрос.

## 6. Управление

### 6.1. Команды

Сообщения kind 9 с упоминанием агента, текст совпадает точно:

| Команда | Действие |
|---|---|
| `!compact` | сжать контекст текущей сессии |
| `!restart` | начать заново, глубина «последние» |
| `!restart none` | начать заново «с нуля» |
| `!restart all` | начать заново с «весь тред» |
| `!rotate` | синоним `!restart` |

Harness съедает команду и агенту её не передаёт, как сейчас `!rotate`
(`lib.rs:3424`). Любой другой текст (`!restart foo`) — не команда и уходит
агенту обычным сообщением.

### 6.2. Права

Сейчас `!rotate` дополнительно требует, чтобы автор был владельцем (`lib.rs:3441`).
Новые команды принимаем от любого, кто прошёл входной гейт по `RespondTo`:
владелец, его агенты, allowlist или anyone (`evaluate_listener_event`, `lib.rs:474`).
Сообщение того, кто гейт не прошёл, отбрасывается раньше, без реакции.
`!cancel` и `!shutdown` управляют агентом целиком и остаются только у владельца.

### 6.3. Выполнение

- **`!restart <глубина>`:** если идёт ход, отменяем его, как `!rotate` сейчас;
  запись в хранилище удаляем; для следующего холодного старта запоминаем глубину
  и причину `user_restart:<глубина>` с автором. Новая сессия начнётся со
  следующего обращения к агенту.
- **`!compact`:** отправляем в сессию промпт `/compact`. Если сессии в памяти нет,
  сначала поднимаем её через resume; если идёт ход, ждём окончания.
  - Claude: `/compact` обрабатывает Claude Code, адаптер его учитывает.
  - Codex: текстовый промпт, начинающийся с `/`, разбирается как команда,
    `compact` вызывает `runCompact` (`codex-acp` `index.js:38815`, `:38845`).
- **Сообщение о сжатии.** Оба адаптера присылают `compaction_update`, только если
  клиент объявил `clientCapabilities.session.compaction`. `buzz-acp` его не
  объявляет (`acp.rs:404`), поэтому сейчас сжатие приходит как tool_call
  «Compact conversation», а Desktop распознаёт его по tool_call и хуку
  (`agentSessionToolClassifier.ts:252`). Решение: объявить возможность и научить
  панель активности Desktop рисовать `compaction_update`. Так сжатие типизировано
  и честно сообщает статус `failed`. Автосжатие у лимита отражается как
  `compacted · auto_compact`.
- **Подтверждение.** Сразу после команды агент ничего не пишет, поэтому harness
  ставит реакцию на сообщение с командой: ✅ выполнено, ❌ с причиной.
  Публиковать реакции harness уже умеет (`pool.rs:5559`).
- **Другие агенты.** При подаче контекста треда сообщения-команды исключаются,
  иначе другие агенты увидят `!compact @Агент` и могут на это среагировать.

### 6.4. Desktop

- В строке состояния под ответом агента (раздел 4.3) — меню: «Сжать»,
  «Начать заново» ▸ «с нуля / последние / весь тред».
- Меню видят только те, кого пропускает `RespondTo` этого агента. Окончательно
  права проверяет harness.
- Кнопка отправляет команду от имени пользователя. В треде команда показывается
  компактной системной строкой: «<имя>: сжать контекст <агент> ✅».
- С мобильного и из CLI ту же команду можно набрать руками.

## 7. Ошибки

Принцип: сбой хранилища или файла статуса никогда не роняет ход и не мешает
отправить сообщение. Худший исход — новая сессия с видимой причиной или ответ
без строки состояния.

| Где | Что случилось | Поведение |
|---|---|---|
| Запись | повреждена, не читается, неизвестный формат | считаем, что записи нет; новая сессия `resume_failed:store_unreadable`; файл переименовываем в `.corrupt` |
| Запись | не удалось записать (диск, права) | ход продолжается, предупреждение в лог; следующий resume невозможен → `resume_failed:not_persisted` |
| Запись | падение посреди записи | временный файл в том же каталоге + rename (`tempfile` уже в зависимостях, `crates/buzz-acp/Cargo.toml:27`) |
| Состояние доставки | лимит id исчерпан | отбрасываем самые старые; худший случай — одно повторное сообщение, уже бывшее в истории |
| Resume | таймаут 60 с, ошибка адаптера, удалённый транскрипт | новая сессия `resume_failed:<код>` |
| Два воркера | гонка за скоуп | проверка по поколению, проигравший запись не трогает |
| Файл статуса | нет или повреждён | сообщение уходит без тега, `send` не падает |
| `!compact` | сессии нет | ❌ «нет сессии» |
| `!compact` | `compaction_update` со статусом `failed` или ошибка промпта | ❌ с причиной, сессия прежняя |
| `!restart` | идёт ход | ход отменяется, как при `!rotate` |
| Команда | автор не прошёл `RespondTo` | отброшена на гейте, без реакции |

## 8. Тесты

Правило репозитория: тест бьёт в продакшн-шов и падает без фикса.

1. **`session_store.rs`, unit:** запись и чтение, повреждённый файл, атомарная
   запись, лимит id доставки, сравнение поколений.
2. **`pool.rs` с фейковым ACP-агентом** (bash-скрипт по JSON-RPC через
   `AcpClient::spawn`, как в `pool.rs:7197`; вызывается боевой `run_prompt_task`):
   - resume объявлен → `session/resume`, а не `session/new`;
   - resume вернул ошибку → новая сессия `resume_failed:…`;
   - resume не объявлен → новая сессия без попытки;
   - после resume только дельта: тред отдаёт локальный HTTP-сервер
     (приём `counting_resolver`, `pool.rs:10834`), старые сообщения не повторяются;
   - холодный старт: первое упоминание агента вне окна попадает в промпт;
     глубины `none`/`recent`/`all`;
   - `usage_update` от Claude и Codex → файл статуса с процентом.
3. **Команды:** разбор `!compact`, `!restart [none|all]`, `!rotate`; права через
   `evaluate_listener_event` (существующие тесты гейта — `lib.rs:7612`, `:7722`);
   команды не попадают в контекст других агентов.
4. **CLI:** `messages send` с переменной окружения и файлом статуса ставит тег;
   без файла или с битым файлом — без тега и без ошибки (тесты отправки уже
   работают с локальным мок-сервером, `messages.rs:1724`).
5. **Desktop:** разбор тега и текст строки, видимость меню по `RespondTo`,
   компактная строка команды, отрисовка `compaction_update`; `node --test`.
6. **Главный цикл `run_harness`.** Его не вызывает ни один тест: единственный
   вызов — точка входа (`lib.rs:2608`). Сон пула, respawn и shutdown живут в нём.
   - Решения выносим в чистые функции `session_store.rs` и покрываем unit-тестами;
     в `run_harness` остаётся вызов в одну строку (прецедент — `idle_pool_sleep_due`).

## 9. Форк и приёмка

- **Реестр.** Каждый новый и изменённый файл регистрируется в
  `scripts/fork/patches.json` с символами и швами вызова. Шов проверяется
  удалением: `sync.py validate` должен упасть. Затем `sync.py render`.
- **Локальная приёмка** по `TESTING.md`, раздел «ACP Harness»: локальный релей,
  `buzz-acp` с `BUZZ_ACP_IDLE_POOL_SLEEP=60`, Claude и Codex в одном треде:
  - продолжение после сна с процентом;
  - новая сессия при провале resume (транскрипт удалён);

  - отказ постороннему;
  - первое упоминание агента в длинном треде.
