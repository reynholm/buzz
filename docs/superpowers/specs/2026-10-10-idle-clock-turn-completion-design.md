# Buzz fork: часы простоя обновляются при завершении хода

Дата: 2026-10-10. Статус: дизайн на ревью владельца, код не реализован.
Ветка: `fork/session-continuity`. База: `fork/main`, `bb99d224a81aa25808101c48442f9e7b2b8563c5`.
Задача форка: reynholm/buzz#7. Upstream: block/buzz#7171 (issue), block/buzz#7173 (PR, открыт).
Кусок 1 из спеки `2026-10-10-session-continuity-design.md`.

## 1. Проблема

Часы простоя ленивого пула двигаются только при dispatch хода: `last_activity`
обновляется в `crates/buzz-acp/src/lib.rs:2894`, `:3636`, `:4903`. Завершение хода
их не трогает. Ход длиннее `BUZZ_ACP_IDLE_POOL_SLEEP` (Desktop ставит 900 с,
`agent_env.rs:16`) в момент завершения уже выглядит простоем, и первый же тик
усыпляет пул: сессия, её фоновые задачи и запланированные пробуждения
пропадают сразу после ответа.

## 2. Решение: порт block/buzz#7173

- Обновление часов простоя переносится в `handle_prompt_result`
  (`lib.rs:5008`), поэтому существующие тесты обработки результата
  стерегут и эту проводку.
- Решение «продлевает ли результат жизнь пула» — исчерпывающий `match`
  по `PromptSource`: новый вариант обязан явно решить.
- Результаты heartbeat часы не обновляют: иначе пул с heartbeat не уснёт никогда.
- Подтверждение steer тоже считается активностью.

Известные края PR (не меняются): ход дольше `max_turn_duration + 100s`
истекает сам, и пул может уснуть до конца хода; путь panic часы не обновляет.

## 3. Применимость к форку

PR правит один файл, `lib.rs` (+191/−0). Проверка `git apply --reject` на
`bb99d224a`: все продакшн-хунки ложатся, отклонён один тестовый хунк
(блок вспомогательных функций в `error_outcome_emission_tests`). Его переносим
руками. Трёхсторонний merge в локальном клоне невозможен: история обрезана,
`git merge-tree` отвечает «unrelated histories». Компиляцию покажет только сборка.

Когда upstream примет #7173, запись в реестре форка схлопнется при синхронизации.

## 4. Тесты

1. Тесты из PR: `result_refreshes_idle_clock` (соответствие вариантов
   `PromptSource`), результат канала через `handle_prompt_result` обновляет
   часы, результат heartbeat — нет.
2. Стенд `run_harness` (спека сессий, раздел 8, п. 6): фейковый релей и фейковый
   ACP-агент. Сценарий для #7: ход длиннее порога сна → ответ → пул не засыпает
   до истечения порога после ответа. Тот же стенд потом используют куски 2–4.
   Объём фейкового релея (набор WS-сообщений при старте harness) определяется
   в плане; REST-клиент harness обращается только к `/query` и `/events`.
3. Полный прогон пакета:
   `env -u BUZZ_ACP_ALLOWED_RESPOND_TO -u BUZZ_ACP_LAZY_POOL -u BUZZ_ACP_IDLE_POOL_SLEEP cargo test -p buzz-acp -- --test-threads=1`.

## 6. Не входит

Из пунктов reynholm/buzz#7: настройка `BUZZ_ACP_IDLE_POOL_SLEEP` владельцем
(вывод ключа из `RESERVED_ENV_KEYS`, поле в Desktop) и одинаковый `lazy` для всех
путей запуска. С resume (кусок 2) сон пула перестаёт терять контекст, поэтому
к ним возвращаемся только если на практике не хватит.
